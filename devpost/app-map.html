A take-home guide to where things live. Snapshot of commit be45e0c; the code can drift after this, so trust the files over the map.

What it is, in three pieces

The page (public/) shows four screens and keeps the whole quiz in one in-memory object. The server (server.js) hands out the page files and answers two API requests. The AI module (lib/ai.js) is the only code that talks to Claude, and the only place the API key exists.

The route (reference)

Prepared from the finished code. It was not walked interactively in the build session; follow it yourself with the app running (npm start) and the files open.

  1. Stop 1 — the input. public/app.js, search for async function submitAnswer An empty answer becomes "I don't know" right here, without a request. Otherwise it builds the body (question, reference answer, your answer, the notes) and calls api("/api/grade", …). The api helper a few lines above is the only fetch in the app.
  2. Stop 2 — the server. server.js, search for "POST /api/grade" Reads the JSON body, checks the four fields are strings, and hands them to gradeAnswer. The routes table is the whole API: two entries plus status.
  3. Stop 3 — the AI call. lib/ai.js, search for async function askForJson One client.messages.create with a system prompt, your text, and output_config.format set to a JSON schema. The reply text is JSON.parsed and then checked (gradeAnswer verifies the verdict is one of three words). The key is read by new Anthropic() from the environment at the top of the file.
  4. Back to the screen. public/app.js, search for function renderFeedback The grade is stored in session.answers[session.index] and the Feedback screen is built from that entry. After question five, summarize(session.answers) turns the same array into the Results screen.

To change this, start here

  • Number of questions — QUESTION_COUNT in lib/ai.js and public/app.js (both).
  • How strict the grading is — GRADE_PROMPT in lib/ai.js.
  • What counts as "sure but wrong" — studyFirst inside summarize() in public/app.js; the test in test/summarize.test.js will tell you if you broke the maths.
  • The headline sentences — the headline branches in summarize().
  • Colours and fonts — the :root block at the top of public/styles.css. The highlighter is --mark.
  • Word limits — MIN_WORDS / MAX_WORDS in lib/ai.js (server) and public/app.js (page).

A practice to reuse

The decision that saved the most trouble: ask the model for a fixed shape, then check it anyway. spec.md > External Services and Dependencies wrote the two schemas down before any code; lib/ai.js sends them as output_config.format and still validates the parsed reply (five non-empty questions, a verdict from the allowed three). The page never has to guess whether a string is JSON or prose. On another project, write the response shape into the spec first, send it as a schema, and keep a small validation step on your side; the error messages you get are then about your data, not about parsing.

A second one: the score maths lives in a pure function (summarize) that a test can call without a browser or an AI, which is why the Results screen could be verified in seconds (npm test).
